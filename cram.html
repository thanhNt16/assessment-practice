02 SQL Deep Dive: The Problems EPAM Actually Asks
  • Window functions compute per-row values over a frame without collapsing rows — the core difference from GROUP BY.
  • Canonical dedup: ROW_NUMBER() OVER (PARTITION BY key ORDER BY ts DESC, id DESC), keep rn=1 — one scan, deterministic ties.
  • Logical order: FROM/JOIN → WHERE → GROUP BY/HAVING → windows → ORDER BY; WHERE filters rows, HAVING filters groups.
  • SARGable predicates only: CAST(dt AS STRING) full-scans; dt = DATE '2024-01-01' prunes partitions.
  • LEFT JOIN plus WHERE on the right table's column silently becomes an INNER JOIN — move it into ON.
  • Duplicate join keys fan out rows: a 1.1x key duplication silently doubles summed revenue.
  • CTEs get inlined and recomputed — Snowflake: AS MATERIALIZED; Spark: CACHE TABLE.

03 Python & PySpark: Coding Patterns
  • "File won't fit in memory" → generator: yield, don't return — dicts/sets are O(n) RAM, generators O(1).
  • Reach for Spark at >10 GB, multi-file/Parquet input, cross-dataset joins, or "distributed"; plain Python under ~1 GB.
  • Driver OOM: collect()/toPandas(). Executor OOM: skew, repartition(1) before a heavy stage, cache without MEMORY_AND_DISK.
  • UDF ladder: native 1× → pandas UDF ~2–5× (Arrow batches) → Python UDF ~10×+; use F.when, never a UDF, for conditionals.
  • Skew: diagnose via groupBy(col).count().orderBy(desc("count")) or a Spark UI straggler; fix by salting the hot key (16 buckets) + two-stage agg.
  • repartition(n, col) shuffles and balances; coalesce(n) skips the shuffle but can leave skew.
  • Cache only when reused ≥2× (MEMORY_AND_DISK, then unpersist()) — blind .cache() is a memory leak.

04 Distributed Systems Fundamentals
  • CAP forces the C-vs-A choice only under a network partition: CP refuses stale answers (ZooKeeper, etcd), AP serves possibly stale (Cassandra, DynamoDB).
  • Quorum rule: R + W > N forces read/write overlap; W > N/2 prevents split-brain.
  • N=5 math: W=3/R=3 → 99.1% both paths; W=1/R=5 → ~99.999% writes but 59.0% reads.
  • Retries are mandatory → at-least-once delivery → duplicates guaranteed; idempotency keys, dedup tables, upserts make replays no-ops.
  • "Exactly-once" is effectively-once end-to-end: idempotent producer + transactional offsets + a sink that participates in commit.
  • Wall clocks lie across machines — order with event time + watermarks; LWW silently discards concurrent updates.
  • 2PC is atomic but blocking (crashed coordinator holds locks); sagas chain local transactions with compensations.

Only during a network partition — before that you get both consistency and availability.

06 Batch vs Streaming
  • Batch answers "what is true given all data up to now" (bounded); streaming "what is true right now" (unbounded) — the trade is latency vs reprocessing/state cost, not throughput.
  • Escalation path: batch → micro-batch (Spark SS ~500 ms floor) → true streaming (Flink/Kafka Streams 10–100 ms); each step up is a permanent tax: state ops, checkpoints, watermark tuning.
  • Only event time is reproducible; processing time is for lag monitoring.
  • Watermark W = maxObservedEventTime − allowedLateness (typ. 20 s–5 min); a window emits when W passes its end; W = min across partitions, so one idle source stalls everything.
  • Late events: within allowedLateness → re-accumulate and re-fire (retraction); beyond → side output or dead-letter queue.
  • State (windows, join buffers, dedup keys) needs a TTL or it grows forever.
  • Exactly-once exists only end-to-end: replayable source + exactly-once state + transactional/idempotent sink — else at-least-once plus dedupe.

Latency vs reprocessing/state cost — never throughput.

07 Data Warehouse vs Data Lake vs Lakehouse
  • Four generations, each failure mode the next's feature list: EDW → lake → cloud DW → lakehouse; answer "why the transition" with failure mechanisms, not product names.
  • Lakes failed structurally (60–85% of big-data projects abandoned): no atomic commits, no schema enforcement, no compaction, no governance.
  • Lakehouse = Parquet + transactional table format + object storage + catalog + any engine — the format + catalog is the platform.
  • Cloud DW disaggregation (micro-partitions ~16 MB with min/max pruning, isolated virtual warehouses, per-second auto-suspend) vs shared-nothing rebalancing cost.
  • Lakehouse contribution: schema-on-write with late binding — enforce at commit, evolve without rewriting files.
  • ELT displaced ETL where storage/compute decoupled; ETL survives at trust boundaries (PII masking before load, cross-region).
  • Cost rule: utilization <30% → per-second auto-suspend; >60% sustained → always-on/reserved; watch egress and per-TB-scanned ($6.25/TB BigQuery).

⚙️ Technology Deep-Dive

09 Table Formats: Delta Lake vs Iceberg vs Hudi
  • A table format adds what Parquet lacks: atomic commits, updates/deletes, schema/partition evolution, and pruning metadata over immutable files.
  • Delta is a log: _delta_log JSON commits + Parquet checkpoint every 10th commit, optimistic concurrency, Deletion Vectors since 2.x.
  • Iceberg is a tree: catalog CAS pointer → metadata.json → manifest list → manifests → data files, with pruning summaries at every level.
  • Hidden partitioning: transforms (days(ts), bucket(16, user_id)) live in the spec — partition evolution is metadata-only, no rewrite.
  • Hudi is a timeline of instants (the WAL) over file groups; CoW rewrites bases, MoR appends logs until compaction folds them.
  • Delete cost ladder: CoW rewrite → position deletes → DV bitmaps → MoR log records — write cost falls, read cost rises. GDPR deletes: DVs make them KB-scale.
  • Time travel = replay; only VACUUM/expire_snapshots/clean truly deletes. Benchmarks are vendor-shaped — decide from estate: Iceberg multi-engine, Delta Databricks, Hudi keyed CDC.

10 Compute Engines: Spark vs Flink
  • Spark is a batch engine that grew micro-batch streaming; Flink is a streaming engine where batch is just a bounded stream — scheduling, state, failure handling follow from that.
  • Latency floors: Spark ~batch interval (0.5–10 s, p99 pinned by batch commit); Flink ~10 ms record-at-a-time.
  • Spark pipeline: lazy plans → Catalyst (pushdown, join choice, whole-stage codegen) → stages cut at shuffle boundaries; AQE coalesces and skew-splits at runtime; RocksDB state store default since 4.0.
  • Flink exactly-once = rewindable source + async barrier snapshot (Chandy–Lamport) + TwoPhaseCommittingSink (pre-commit at checkpoint, commit on notifyCheckpointComplete).
  • Unaligned checkpoints under backpressure: barriers overtake in-flight buffers — larger snapshots, steady duration.
  • AQE skew rule: partition > 256 MB and > 5× median → split into ~64 MB subtasks (512 GB straggler: 60 min → 8 min, −87%); salting is the fallback costing two shuffles.
  • Set TTL on every keyed Flink op — unbounded state is the #1 production killer; checkpoint interval bounds 2PC deliverable latency.

Spark runs incremental micro-batches; Flink processes record-at-a-time, with batch as a bounded stream.

11 Spark Performance: Catalyst, AQE & Tuning
  • Catalyst: rule-based logical optimization (pushdown, pruning, folding) + cost-based physical planning; without ANALYZE TABLE, sizeInBytes defaults huge so auto-broadcast never fires at compile time.
  • AQE re-plans at each shuffle boundary from actual map-output stats — default since 3.2: coalesce toward ~64 MB, skew-join split, SMJ→BHJ/SHJ switch; useless without an Exchange.
  • AQE skew-join split fires only above BOTH thresholds: > 5× median partition AND > 256 MB — joins only; groupBy skew needs salting.
  • Join choice = one threshold + honest stats: broadcast ≤ 10 MB (misestimate → driver OOM), SHJ on hint, SMJ the robust default.
  • Size partitions ≈ shuffle bytes ÷ 128–256 MB — the 200 default is wrong in both directions; over-provision and let AQE coalesce (it cannot split ordinary oversized partitions).
  • Unified memory (fraction 0.6): storage evicts, execution spills; G1GC for ≥4–8 GB heaps; GC > 10–15% of task time = allocation churn.
  • Diagnose from the UI: max ≫ p50 → skew; spill counters → memory; fix data shape before knobs.

12 Messaging & Streaming Backbones: Kafka and Friends
  • Three messaging models: queue (one consumer, ack-then-delete), pub/sub (fan-out, no replay), log (Kafka: partitioned, replayable, consumer-owned offsets — replay is an offset reset).
  • Ordering is per-partition only: hash(key) % partitions gives per-entity order; changing partition count silently breaks the key map.
  • ISR = replicas current within replica.lag.time.max.ms (30 s); high watermark = highest offset replicated to all ISR — consumers read only up to HW.
  • Durability recipe: acks=all + RF=3 + min.insync.replicas=2 + unclean.leader.election.enable=false; ISR shrunk to 1 → explicit NOT_ENOUGH_REPLICAS, not silent loss.
  • Exactly-once stops at Kafka's edge: idempotent producer (PID + sequence, default since 3.0) + transactions + read_committed; across boundaries use the outbox — never dual-write.
  • Rebalance-proofing: cooperative-sticky assignor (KIP-429) + static membership + max.poll.records finishing inside max.poll.interval.ms (5 min default).
  • KRaft replaced ZooKeeper (removed in 4.0, 2025); schema evolution FULL_TRANSITIVE on shared topics; tiered storage decouples retention from broker disk.

🏁 Production & Defense

13 Pipeline Reliability: Testing, Quality, Observability
  • Six quality dimensions are the shared vocabulary: accuracy, completeness, freshness, validity, uniqueness, consistency — every tool (GE, dbt, Soda) maps to them.
  • Test pyramid: unit tests every PR, data tests every pipeline run, expensive reconciliations daily/before publish, production monitoring continuous.
  • Observability = metrics (what broke) + logs (where) + lineage (what else); OpenLineage/Marquez bounds the blast radius.
  • Gate failure → circuit breaker: publish to staging, promote atomically — consumers keep last-known-good; alert when quarantine rate exceeds ~1%.
  • SLO math: 99% on-time over 30 daily runs → error budget 0.3 runs → page on the first miss; thresholds come from budget math, not complaints.
  • Idempotent backfill: DELETE + INSERT per partition or MERGE — never blind append; same input must give same output.
  • Incident loop: alert → classify → contain → fix → backfill → verify → blameless postmortem; every incident ends as a new automated check.

16 Generative AI System Design (Aminian & Sheng)
  • The skeleton is the transferable asset: clarify requirements → frame as ML task → data → model → eval → system design + deployment/monitoring — one rehearsal covers any prompt.
  • Model choice is requirements arithmetic, not fashion: one-pass latency → GAN/VAE, ceiling quality → diffusion, resolution at scale → AR, video economics → latent diffusion.
  • Exhaust retrieval + prompts before finetuning: finetuning can't cite sources and needs constant retraining; RAFT only when retrieval is fixed and answers are still bad.
  • RAG pipeline: parse → chunk (500 chars, 200 overlap) → embed → ANN-index; size it explicitly — 5M pages → 40M chunks, +20%/yr.
  • Retrieval quality is the ceiling: a better LLM cannot fix bad chunks.
  • Pair offline metrics (BLEU, CIDEr, CLIPScore, FID/FVD, DINO) with online business metrics (CTR, adoption, cost per user) — naming both unprompted is the scoring behavior.
  • Deployment is a named stage: safety chain, serving, monitoring, retraining loops — users re-rolling seeds quietly multiplies GPU spend.

17 Machine Learning System Design Interview (Aminian & Xu)
  • All 11 chapters share one 7-step skeleton: clarify → frame as ML task → data prep → model development → evaluate → deploy/serve → monitor.
  • The load-bearing move is business goal → ML objective with failure modes named: clicks reward clickbait, completions bias short videos → maximize relevant watch time.
  • Model ladder: popularity baseline → LR → DNN → ensemble only if needed; GBDT is rejected in continual-learning systems — no fine-tuning, retrain from scratch.

18 Machine Translation (Google Translate)
  • Translation = seq2seq → encoder-decoder Transformer: bidirectional encoder, causally-masked decoder with cross-attention; chosen for variable-length I/O and source understanding.
  • Scope first: 4 languages (EN/ES/KO/FR), auto language detection (encoder-only classifier routes the fleet), inputs ≤ 1,000 words, 300M sentence pairs.
  • Two-stage training: masked-LM pretraining (next-token would let the encoder leak the answer) then supervised next-token finetuning; start from T5/BART checkpoints to skip stage 1.
  • Keep preprocessing that preserves grammar; drop legacy lowercasing/stemming/stop-words; subword BPE with </w> boundary tokens solves vocabulary size and OOV.
  • Placeholder named entities (ENTITY_1) in, restored after decoding — models choke on uncommon proper nouns.
  • Beam search, not stochastic sampling — determinism is a feature in translation.
  • Evaluate three ways: BLEU (precision, punishes rewording), ROUGE (recall), METEOR (synonyms, best human correlation) + online feedback; never trust BLEU alone.

19 Personal Assistant Chatbot
  • Requirements before architecture: text-in/text-out, English-only, strict safety, ≥ 4096-token context, follow-ups in session, 80K (instruction, answer) pairs → decoder-only LLM.
  • Three stages, three jobs: pretraining (trillions of tokens, 1000s GPUs, months) buys knowledge; SFT (10K–100K demos) turns continuer into responder; RLHF (100K–1M comparisons → reward model → PPO/DPO) aligns.
  • Data quality inverts across stages: trillions of low-quality web tokens → small expert demonstrations → ranked comparisons; rank, never score — annotator numbers drift.

23 High-Resolution Image Synthesis
  • Requirements: 5M natural-scene images, unconditional generation, 1024²–2048² output, ~5 s per image — not real-time.
  • Latency math picks the model: pixel-level autoregression is O(N²) (~1M steps at 1024²) and diffusion is O(T·N²) (minutes); chunk tokens at 64×64 px/token cut it to 256 steps — seconds.
  • VQ-VAE tokenizer: CNN encoder → nearest-neighbor codebook quantizer → transposed-conv decoder; discrete latents kill posterior collapse and shrink the prediction space to k tokens.
  • Stage I losses weighted: reconstruction (MSE) + quantization (stop-gradient) + perceptual (VGG features) + adversarial (patch-based); MSE-only shows artifacts at high res.
  • Nearest-neighbor lookup has no gradient — straight-through gradient copies decoder gradients to the encoder.
  • Two independently trained models composed at inference: tokenizer (reconstruction) + generator (decoder-only Transformer, next-token cross-entropy over cached sequences).
  • Serving mirrors the split: generation service, decoding service (encoder never ships), 2× super-resolution (RCAN/ESRGAN) for 2048²; gate on quality plus time and cost per image.

Chunked AR is 256 token steps (seconds); diffusion is O(T·N²) with more steps at high res — minutes.

A powerful decoder ignores its latents at high res; discrete codebook tokens force it to use them.
